## Индивидуальный проект

**Название проекта:** Система организации дискуссионных клубов
(Discussion Club Management System).

**Что переработано на ПР3.** Проект ПР2 не создавался заново: его
функциональная модель (коллекции словарей и функции) преобразована в
объектную модель. Коллекции проекта изменились с `dict[int, dict]` и
`list[dict]` на списки объектов `List[Club]`, `List[Topic]`, `List[Event]`
и `List[Registration]`. Формат JSON-файлов, набор функций и интерфейс
приложения сохранены, поэтому результат сценария ПР1 не изменился:
автоматическая демонстрация по-прежнему даёт 24 подтверждённых участника
из 25 мест.

**Основные классы, добавленные на ПР3** (пакет `models`, отдельный модуль
на каждый класс, импорт через относительные импорты и реэкспорт в
`models/__init__.py`):

| Класс          | Назначение | Основные атрибуты |
|----------------|------------|-------------------|
| `BaseEntity`   | Общая основа для всех сущностей | `_id`, классовый атрибут `KIND` |
| `Club`         | Дискуссионный клуб | `id`, `name`, `description`, `moderator` |
| `Topic`        | Тема дискуссии | `id`, `title`, `level`, `tags`, `materials` |
| `Event`        | Мероприятие клуба | `id`, `club_id`, `topic_id`, `event_date`, `start_time`, `format`, `place`, `capacity`, `min_age`, `required_level`, ссылки `club` и `topic` |
| `Registration` | Заявка участника на мероприятие | `id`, `event_id`, `name`, `age`, `level`, `has_read_materials`, `status`, `ticket_code`, `confirmed_at`, ссылка `event` |

Каждый класс реализует `__init__()` с аннотациями типов, `__str__()`
(через переопределяемый метод `describe()`), преобразование в данные `to_dict()`
и создание из данных `from_data()` (метод класса).

**Перенос функций в методы объектов:**

* `Event.status_on()` и `Event.free_places()` — статус мероприятия по дате и
  число свободных мест (соответственно `get_event_status()` и
  `get_free_places()` ПР2);
* `Event.check_requirements()` — проверка требований мероприятия к участнику
  по собственным атрибутам `min_age` и `required_level`;
* `Event.link()`, `Registration.link()` — установка связей между объектами;
* `Registration.confirm()` и `Registration.cancel()` — изменение состояния
  заявки; объект остаётся в коллекции и перестаёт занимать место;
* `Club.matches()`, `Topic.has_tag()`, `Topic.has_level()` — сравнения,
  относящиеся к самому объекту;
* `Registration.generate_ticket_code()` — статический метод создания кода
  участия.

**Инкапсуляция.** Вместимость мероприятия (`Event.capacity`) и статус заявки
(`Registration.status`) — свойства с проверкой значения: отрицательная
вместимость и неизвестный статус приводят к `ValueError`. Список тегов
`Topic.tags` возвращается кортежем, поэтому изменить данные темы по ссылке
невозможно. Идентификатор хранится в защищённом атрибуте `_id` класса
`BaseEntity` и доступен только через свойство `id`.

**Наследование и полиморфизм.** Все четыре класса наследуют `BaseEntity`:
общие `__str__()`, `__repr__()`, `__eq__()`, `__hash__()` и `to_dict()`
определены один раз, а классы переопределяют только `describe()` и
`render()`. Один и тот же вызов `str(entity)` или `entity.render()` даёт
разный результат в зависимости от класса — это используется в
`analytics.describe_entities()` и в пункте меню «Показать объекты и их
методы».

**Композиция.** `Event` хранит ссылки на объекты `Club` и `Topic`,
`Registration` — на объект `Event`. Поэтому `Registration.event_date_text()`
получает дату мероприятия, а карточка `Event.render()` собирается из данных
связанных объектов без поиска в коллекциях.

**Декораторы.** В проекте применены `@property`, `@staticmethod`
(`Registration.generate_ticket_code()`), `@classmethod` (`from_data()`) и
пользовательский декоратор `@logged` с `functools.wraps` из `utils.py`:
он записывает имена вызовов `storage.load_json()` и `storage.save_json()`
в журнал `CALL_LOG`, не меняя результат функций.

**Преобразование данных.** JSON-файлы не изменились. При загрузке
`storage.load_json()` читает записи, а методы `from_data()` создают объекты;
при сохранении `objects_to_records()` вызывает `to_dict()` каждого объекта.
В файле остаются идентификаторы связанных объектов (`club_id`, `topic_id`,
`event_id`), а обратные ссылки восстанавливаются функцией
`storage.bind_references()`. Обработка исключений сохранена: отсутствующий или
повреждённый файл и запись с неверной датой не прерывают работу программы.

**Тесты и качество кода.** Все тесты ПР2 адаптированы к объектной модели, новый
файл `tests/test_models.py` проверяет классы и принципы ООП. Всего 281 тест,
все проходят; `flake8` не обнаруживает замечаний.

## Результат работы

В результате выполнения ПР3:

* основные сущности предметной области представлены классами и объектами:
  `Club`, `Topic`, `Event`, `Registration` в пакете `models`;
* данные и поведение объединены в объектах, реализованы атрибуты, методы,
  `__init__()` и `__str__()`;
* организовано взаимодействие объектов: мероприятие связано с клубом и темой,
  заявка — с мероприятием;
* рассмотрены инкапсуляция (свойства с проверкой, скрытый список тегов),
  наследование (общий базовый класс `BaseEntity`) и полиморфизм (единый
  интерфейс `describe()` и `render()`);
* коллекции проекта содержат объекты предметной области: `List[Club]`,
  `List[Topic]`, `List[Event]`, `List[Registration]`;
* существующие функции ПР2 переработаны с учётом объектной модели: операции
  со смежными сущностями перенесены в методы объектов, функции сохранены там,
  где обрабатывается коллекция;
* сценарий ПР1 не потерян: демонстрация даёт те же решения по заявкам и тот же
  итог — 24 подтверждённых участника из 25 мест;
* сохранена работа с JSON-файлами: загрузка создаёт объекты, сохранение
  преобразует их обратно в данные;
* сохранены обработка исключений, аннотации типов, документирование и
  интроспекция (режим 4 теперь показывает и классы проекта);
* изученные декораторы применены в проекте: `@property`, `@staticmethod`,
  `@classmethod` и пользовательский `@logged`;
* меню приложения дополнено пунктом «Показать объекты и их методы»;
* обновлён `README.md`: добавлены описания классов, атрибутов, методов,
  взаимодействия объектов, распределение ответственности между объектами и
  функциями, структура проекта и сведения о тестах;
* результат зафиксирован в Git коммитом с меткой `PR3` и отправлен в удалённый
  репозиторий.

## Вывод

Практическая работа выполнена полностью. Индивидуальный проект переведён с
функциональной модели на объектно-ориентированную без потери функциональности:
сценарий ПР1 работает с прежним результатом, файлы данных сохраняют прежний
формат, а набор команд пользователя не изменился.

Освоенные принципы ООП применены осмысленно, а не формально. Наследование
оправдано повторно используемым кодом базового класса, полиморфизм —
единым интерфейсом вывода карточек и строковых представлений, инкапсуляция —
защитой данных объекта (вместимость, статус, теги), композиция — устранением
повторного поиска связанных объектов в коллекциях. Декоратор `@logged`
показывает, как функцию можно дополнить поведением, не изменяя её код.

Проверка `flake8` завершается без замечаний, 281 тест `pytest` подтверждают
работу классов, функций и сценариев меню, а данные приложения корректно
переживают цикл «загрузка — изменение — сохранение».

Проект подготовлен к следующему этапу: объектная модель предметной области
полностью отделена от способа хранения данных, поэтому при переходе к Django
классы Club, Topic, Event и Registration станут прообразом моделей ORM, а
связи, реализованные композицией, — внешними ключами.
